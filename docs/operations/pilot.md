# Supervised pilot runbook

This is a test plan, **not an automatic executor or account authorization**. The coordinator has accepted [roadmap 08's supervised personal-account round on Linux](../internals/validation.md#checkpoint-08--supervised-personal-pilot-accepted), including the downstream adapter and one human-clip transcription composition. Offline packaging remains separate evidence. Any further run needs its own approved account, exact conversations and operations; this acceptance grants no production deployment or rollout. Do not activate/pair an account, send, mutate chats, install a service or publish a release during preparation.

## Before the round

The coordinator records privately: owner approval; deployment/account and data directory; any downstream configuration selection; exact target JIDs and permitted operations; file/card sharing permission; time window; phone observer; and stop conditions. Use two approved accounts for meaningful 1:1 delivery/read distinctions. Keep organization rules and integration configuration in the consuming repository.

Install the chosen [exact source commit](release.md), record commit/lock/toolchain/build hashes, and correlate the new daemon PID with that immutable path after normal exit of its predecessor. No other runtime/probe may own that directory. Confirm authenticated open status, expected account and exact restriction. A status check and the following command are not atomic against external daemon replacement; coordinate ownership throughout the round and stop on a changed PID/account/configuration.

All CLI invocations below use the same approved absolute CLI path and explicit `--data-dir`. The existing [agent command examples](../user/agents.md) contain fictional identifiers, not approved targets. Select a stable unique key per intended action **before** its first invocation; record exact arguments, byte manifest and key privately. Reuse those keys after reconnect/restart. A new key is another operation, not a timeout retry. Do not invent failure/outage scenarios requiring unapproved account or host-network changes.

## Uncertainty and acceptance

For timeout/error, inspect the original key first; the command may still be in flight. `request.data: null` is no recorded intent yet, not proof of cancellation. A persisted uncertain intent must never be retried with a new key or automatically resent. An exact same-key query/repetition returns original evidence; conflicting arguments fail. Keep unknown legacy receipts unknown. Do not induce a live uncertain send merely to test this: injected offline failures cover it; apply the procedure if uncertainty naturally occurs.

Record each step as **observed**, **partial**, **unknown**, **blocked** or **not run**, with separate phone effect and later client evidence where required. Stop on wrong account/target, ambiguous identity/media, unexpected pairing, terminal recovery, private-data exposure or any need for broader authorization. A missing event/receipt is unknown, not nondelivery; an open connection cannot clear the historical decryption issue. Preserve state and report the gap rather than deleting locks/credentials or forcing a restart.

The [accepted checkpoint 06](../internals/validation.md#checkpoint-06--essential-flow-accepted) is prior coordinator-reported evidence, not a run of this pilot. It covers document/card phone effects, byte-identical downloads including synthetic linked-account Opus (`fromMe: true`), chat changes, restart/brief WebSocket recovery, an existing 1:1 reply and a new proven-route send with separate pre-open delivery and later read evidence. It does not establish human-speech STT, real first contact, prolonged physical outage, complete history/catch-up, resolved historical decryption, macOS execution or the downstream deployment account.

The coordinator accepted the [subsequent personal technical round](../internals/validation.md#checkpoint-08--supervised-personal-pilot-accepted) with uncertainty and limits retained: group receipts stayed unknown, read/unread needed later phone-originated observations, and the new own-group document was not downloaded through the adapter because its SDK return lacked an explicit participant. A single received human clip established transcription availability/composition, not broad quality. No new quote/deletion or 1:1 receipt validation was claimed. This closes **08 for that supervised scope**; any further run requires the coordinator's own evidence and acceptance. Do not create an npm/GitHub release, tag, service or broader rollout as a consequence of this acceptance or an offline candidate passing.
