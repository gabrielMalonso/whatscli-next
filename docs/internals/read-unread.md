# Read/unread internals

See [chat-state usage](../user/chat-state.md) for public counter and pending-state rules. These implementation notes describe the pinned Baileys API.

## SDK observations

`chatModify` creates a `regular_low` app-state patch containing `markChatAsReadAction` and a message range. `appPatch` resynchronizes, sends the encoded patch, and saves its version. The CLI does not separately call `readMessages` or send an additional message read receipt.

The pinned rc14 package includes the fork changes and the typed-echo source patch; see [provenance and regeneration](../../patches/README.md). `chatModify` receives the immutable key as local `requestId`. Its unbuffered `patch-response` is projected into `request.appStateResponse` and a narrow `app-state.response` journal entry, inside one Store transaction. Only known non-send requests in `regular_low` can acquire that evidence. The first valid response is retained; duplicates cannot downgrade it or alter newer pending intents. No chat state or message receipt is advanced by this event. `perform` reloads the record on completion, preserving a response even if the SDK subsequently throws.

The runtime uses `emitOwnEvents: false`. The patched SDK emits its narrow `local-echo` chat action independently of that setting, with the original local `requestId`. Only a matching non-send request, action kind, conversation and current pending key can populate `sdkReported`, with source `sdk-local-echo`. Existing persisted `sdk-event-during-request` reports remain readable with their original, weaker invocation-context meaning. Neither source updates observed chat state or discharges pending.

Legacy synthetic chat and outgoing message events are disabled. Independent preflight sync observations remain eligible even while a command is running; async invocation context no longer classifies their origin. Every listener is still bound to its socket's ownership token, so a replaced socket cannot write evidence. A separate outgoing network echo remains observable.

Independent read/archive fields are applied once, before the SDK buffer consolidates them. A conditional update is applied only when the SDK accepts its condition. A small per-field capture-order watermark prevents an older deferred condition from overriding a later accepted field. Pending resolution compares the request key present at capture. Consolidated callbacks store metadata and content without reapplying these fields, so they cannot settle a later intent or reverse an absolute zero. A decoded `sync` action remains journal/coverage evidence until the corresponding chat update is accepted; it is not automatically promoted to current chat state.

SDK reports persist separately from chats. A newer intent clears its field's previous report, sufficient independent state removes it, and a late event cannot overwrite either. A return without an event does not create a report, and old requests are never backfilled from requested values. An event before an interrupted SDK call remains SDK evidence alongside the uncertain request outcome.

Noninitial remote read actions emit counter 0 or -1. The callback omits remote action time, message range, request key, and direction. Initial synchronization can produce neutral null. Buffering can wait for a chat, discard an old range, or absorb updates into history. Incoming messages produce increments that can combine with read actions. These counters are not reliable absolute totals.

## Pending state

Any valid counter (0, -1, or positive), or manual-unread true, can establish state and clear pending and the previous SDK report for that field. Positive evidence means unread with an unknown total, whether or not a read/unread intent was pending. Null or missing fields and manual false remain insufficient. The original request and its outcome are preserved; superseding pending does not confirm the requested phone effect.

Incoming messages received online or from an offline backlog produce positive counters through the existing SDK chat-update path. The runtime does not add a separate unread transition when storing a message. Positive history counters and duplicate increments can also establish unread, including after a read observation. This is a local interpretation of SDK evidence, not proof of remote freshness. Accepted capture order is preserved: read followed by an incoming increment establishes unread, while an increment followed by an explicit zero establishes read. An increment removed later by buffered READ still establishes unread evidence and can supersede pending; only qualified complete receipt coverage can subsequently establish zero.

The selected message range comes from local history and may not include the latest remote message. A callback cannot be matched to that range. A contrary explicit state can clear pending; insufficient evidence leaves it pending across restarts. Neither arrival time nor clearing pending proves freshness, causation, or the requested phone effect.

Archive uses the same app-patch path. Different timing or decryption warnings do not establish stronger confirmation or explain a divergence.

List selection uses pending intent values for boolean filters by default, without replacing observed values in `chatView`. `matchedBy` records only the fields selected through intent. Unknown filters and `observedOnly: true` use observed values, including null pending state. Both paths filter in SQL before ordering and pagination. A response does not discharge pending: pending means missing state observation, not missing IQ response.

When changing this behavior, cover both mutation directions, event-buffer ordering, duplicate increments, history, restart, and exact-key replay in `test/read-unread.test.ts` and `test/pending.test.ts`.

## Own-device message reads

Direct delivery/read/played receipts no longer put the receipt time in `messageTimestamp`. The SDK keeps its status update and exposes a separate per-message receipt with the origin `userJid` and a timestamp in seconds. See upstream [issue #2726](https://github.com/WhiskeySockets/Baileys/issues/2726) and the [buffer-only proposal #2804](https://github.com/WhiskeySockets/Baileys/pull/2804). The fork fixes the source projection, covering both live updates and buffered merge orders. Existing timestamps already overwritten in SQLite are not rewritten from guesses.

The CLI recognizes a direct incoming read only when the receipt user is the current account's PN or LID and the exact incoming key exists. A READ status by itself, peer receipts, outgoing keys, groups, unknown IDs and a read time before the message time cannot clear conversation state.

A small persisted range tracks message keys responsible for validated SDK unread increments since a locally observed zero. Every positive update must include exactly the matching number of distinct incoming keys and valid original message times; otherwise coverage is insufficient. Every tracked key must acquire a matching own-device read receipt before the CLI establishes zero again. Partial and duplicate receipts cannot erase a newer unread key. Snapshots, manual unread markers and new read/unread intents invalidate this inference. Unknown or already untracked unread baselines need a separate chat-state observation; no intent or timeout substitutes for one.

The receipt can be absorbed into `messages.upsert.userReceipt` by buffering, or arrive as `message-receipt.update`; both paths use the same checks. The range survives restart, without inferring that unseen remote messages are covered. The public `readObservation` and narrow `chat-read-receipts` journal event identify `source: own-device-receipts` and `scope: tracked-incoming-messages`, with exact IDs, original message times and a separate `readAt` in seconds. This is local coverage of an external read observation, not a new confirmation of a prior CLI command. Archive state and `request.appStateResponse` remain independent.

## Equal-second mutation boundaries and evidence

Chat commands select every stored message at the maximum message timestamp in that exact conversation. Selecting one row was insufficient when two received messages shared a second: `INSERT OR REPLACE` during status updates can reverse their rowid tie break. A single-row selection could then omit the message that arrived last. Keeping the whole timestamp boundary avoids guessing an order and excludes older history. This does not prove that the local boundary contains the latest remote message or that a remote client applied the action.

`app-state.chat-action` journal entries project the SDK's decoded action, exact range and source. A `local-echo` entry can include the locally supplied `requestId`; it describes decoded outgoing data, not an independent observation. A `sync` entry includes representation, initial-sync and MAC-verification qualifiers, without inferred request correlation or originating-device identity. Only the named scalar fields and minimal message keys/times are stored; extra SDK payloads are excluded. These entries do not mutate chat state, clear pending, or strengthen the IQ response.

Without qualified baseline/ordering evidence, the manual-unread-before-arrival case remains an operational gap: `unreadCount=-1` alone does not establish an empty message backlog. The CLI can remain unread while another client shows read. The receipt must not manufacture zero from an unqualified marker. The projection above distinguishes missing chat actions from those that buffering did not project; the qualified transition below uses additional evidence already present in the SDK events.

## Insufficient receipt reconciliation

A validated incoming range can have an observed-read or unqualified manual-unread baseline. The latter retains exact keys to expose message-level evidence and reject retired/duplicate IDs, but is never allowed to establish a conversation zero. Earlier persisted ranges had an implicit observed-zero baseline and remain compatible. Unknown baselines or mismatched batches still cannot create a range.

For a manual baseline, `readReconciliation` persists a narrow diagnostic and `chat-read-insufficient` records it in the public journal. It contains a minimal message ID/original time, receipt time, local capture time and the explicit reason `manual-unread-marker-unconfirmed`. It does not change observed read state, pending, request evidence or filters. The lifecycle is documented in [chat-state usage](../user/chat-state.md#message-read-manual-marker-unconfirmed).

The controlled capture established that message READ and an own-device receipt arrived without a decoded synced read=true action or a chat zero in that observation window. That absence alone neither proves a protocol impossibility nor rules out a local modeling defect. The diagnostic keeps insufficient cases visible while the qualified transition below distinguishes a prior manual marker from a real untracked backlog.

## Manual markers over observed zero

The pinned SDK creates a positive increment for each incoming real message in `processMessage`. `concatChats` combines a preceding negative marker and a later positive delta as `max(previous, 0) + delta`; it does not preserve the negative marker as an additional backlog. The CLI previously derived `markedAsUnread=true` from `-1`, retained it after a positive update, and forced a manual baseline indefinitely. As a result, reconciliation depended on whether the marker and increment shared a flush.

There is another loss at the buffer boundary: a READ absorbed into an incoming upsert decrements the buffered increment and can delete the counter when the delta reaches zero. Multiple increments can also replace embedded chat message keys during concatenation. The runtime applies independent increments and captures their exact IDs before that buffer. A missing post-buffer delta cannot establish a total zero. See upstream [process-message](https://github.com/WhiskeySockets/Baileys/blob/master/src/Utils/process-message.ts) and [event-buffer](https://github.com/WhiskeySockets/Baileys/blob/master/src/Utils/event-buffer.ts).

Qualification requires a known observed zero without pending unread intent, buffered/uncovered unread evidence or an existing range/marker. A new independent synced patch supplies a valid collection version, remote action time in milliseconds and message frontier/keys covering the locally stored latest timestamp boundary. A later complete increment must contain uncached, distinct incoming IDs with original message times strictly after that action and frontier. Only `notify` upserts can validate those members. Every member still needs its own validated read receipt before zero; `readObservation.replacedManualMarker` preserves the boundary used. This replaces a marker with a message range rather than treating `-1` as proof of empty history.

An increment can arrive before the remotely earlier manual action. The existing range retains its original observed-zero message frontier and any prior own-read time. That delayed action can rebase the same range only if its frontier matches, its time precedes every incoming member and follows the prior read, and all ordinary qualification guards hold. Its paired legacy `-1` is consumed once without discarding those newer IDs; every member still requires `notify` and a validated receipt. Cached/replayed IDs, unpaired content and history invalidate the saved frontier. Older persisted ranges without this provenance cannot acquire it retroactively.

New independent sync actions otherwise retire earlier coverage immediately, before their legacy counters flush. Newer initial/snapshot actions advance the watermark and retire qualification but cannot qualify a replacement themselves. Local echoes and already-seen/older versions stay in the journal without retiring newer evidence. New read/unread intents retire their range once, so a late local echo cannot erase coverage created by a later incoming message. The pre-buffer `captured-unread` watermark is persisted transactionally; a crash after an incomplete increment cannot resurrect a stale zero as a qualified baseline. Archive-only intent remains independent.

The SDK emits a raw upsert before its normal unread increment. Incoming keys remain pending until their upserts are projected. Exact complete increments prove range membership; observing content without covered membership retires that coverage. This includes recovered placeholders and append/history without a matching increment. A decoded reaction without a stub is neutral to unread coverage at both capture and message projection, matching the SDK's non-counting behavior. It still reaches message storage and can affect archive through the SDK's account setting. Empty, unknown and undecryptable payloads are not treated as neutral, and lost baselines are never reconstructed retroactively.

A later contentless `CIPHERTEXT` replay cannot replace persisted, decoded content for the exact stored message identity. Capture does not add a new uncovered key, and projection preserves the original body, timestamp, activity and read coverage. Key identity evidence and message/send status remain observable; an independent echo may establish the chat's existence without inferring activity or read state. The journal still records `message-content-unavailable` with `retainedContent: true`, without raw errors. Events carrying new content, including edits coalesced by the SDK buffer, follow the ordinary projection path. A previously partial ciphertext payload, hidden/deleted content or a different chat/direction/incoming participant cannot provide prior decoded knowledge. This guard does not restore an already lost baseline or recover content that the SDK buffer discarded before its first persistence.

History processing can derive `lastMessageRecvTimestamp` from such a replay, including an incoming message outside the chat's one embedded envelope. Activity capture excludes receive times tied to known failed replays across the full history batch and ignores their embedded message times, while retaining other chat timestamps and unknown-message evidence. Consolidated callbacks do not reapply activity. The original SDK history fields remain intact for buffer conditions.

History batches use the same capture guard before SDK buffering. Their chat state is observed at raw emission. All accepted read/archive fields retain their raw values; their buffered metadata projection cannot reapply them. Pending upsert keys survive pairing until projection, independently of whether the old counter can qualify a receipt range. An explicit zero covers only keys captured before it, including paired increments whose upserts have not yet been stored. Rebasing a delayed manual action may retain pending keys only when every key is an exact member of its already qualified range. Those minimal ID/timestamp pairs remain persisted until their delayed messages arrive, so delivery after the snapshot cannot retire a newer range. An absent counter cannot establish that baseline.

The minimal key/time barrier is persisted before forwarding raw upserts, even before the first range exists, since a notify/append type change can synchronously flush earlier receipts inside the SDK. Only the exact ID/timestamp pair consumes it. It survives a crash before flush; observing uncovered content makes a stale zero unknown rather than renewing that read baseline. Every message in an upsert batch is stored before its absorbed receipts are applied, so an early member cannot establish zero before an uncovered later member is seen. Chat deletion retires the range, marker and derived read projections while preserving message history and the action-version watermark; a delayed receipt cannot recreate a deleted conversation or reuse that proof when metadata reappears.

Unknown/positive baselines, snapshots/history, incomplete batches, cached IDs and ambiguous ordering remain unqualified. No local clock or capture timestamp is used to infer remote ordering. Equal-second arrivals or device clock disagreement may therefore still yield insufficient evidence. A remains subject to controlled live retesting for this narrower correction; complete synchronization outside these conditions is not claimed.

## Controlled diagnostic validation

This was a coordinated browser/CLI comparison using four internal messages between owned accounts, separate from automated fictional fixtures. The private report, focused DOM observations and per-step JSON remain outside Git.

All eleven diagnostic checks passed, with no new divergence:

| D03   | Native/adapter chat and archived lists preserved the field in full/compact and normal/observed-only output.                                           |

Restart persistence, invalid/foreign/duplicate/retired receipts, replacement by a newer `readAt` and isolated zero-observation cleanup remain supported by offline regressions, not an additional live test. The live reset and subsequent normal read do not demonstrate isolated-zero cleanup from an existing diagnostic. No synthetic receipts, restart or forced resync were used in this live round. Lifecycle rules remain those documented above; this validation adds no broader guarantee.

At the end of round 4, scenario A remained **open**: manual unread, archive, new message with automatic unarchive, archive again, then browser menu read left the CLI unread while the browser showed read. That approval covered the diagnostic surface only. Operationally, an unqualified conversation can remain eligible for unread queues; consumers must preserve the insufficient-evidence qualifier rather than silently treating it as reconciled read or repeating a command. Round 4 itself required no new candidate; the subsequent baseline/buffer investigation produced the qualified transition above. PRs remain open for independent review, without merge authorization.
