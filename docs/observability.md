# Persistent, local opt-in observability

New data directories have observability **off**. Enable once for the selected directory; the preference survives CLI exit and normal daemon stop/start:

```sh
node dist/src/cli.js --data-dir /absolute/private/example-session observability enable
node dist/src/cli.js --data-dir /absolute/private/example-session observability status
node dist/src/cli.js --data-dir /absolute/private/example-session observability disable
```

These commands work while stopped and do not open SQLite, pair, connect to WhatsApp or start a daemon. Ordinary consumers keep using the existing commands without logging calls, extra prompts or success reports. Nothing is uploaded. Full/compact response content and error/exit behavior remain the same, with additive observability diagnostics in `status.data.observability`.

Configuration is an owned 0600 `observability.json` in the selected private data directory. Its versioned preference, generation and random local HMAC secret are atomically replaced through one exclusively created pending file, with the complete byte count checked and synchronized before rename. A short write returns `LOCAL_STATE`, preserving the prior preference and incomplete pending file without publishing it. Configuration acquires the append lock, then the separate loss-witness lock, both without waiting. Concurrent updates or a witness currently being written can return `LOCAL_STATE` (including an opt-out that has not committed); there is no silent lost update or retry. A failure can leave a pending file, or a preference already renamed before cleanup failed: inspect status; the error explicitly says persistence may have happened. Existing unknown/incompatible configuration, permissions, pending files and locks are preserved. The secret is never returned by status/query or copied into telemetry.

The runtime watches the data directory for preference replacement and rechecks at command admission and immediately before each log write. `enable`/`disable` also asks an existing compatible daemon to reconcile before reporting its state. A disable cannot race a log append past the configuration commit: both use the same short critical section. An already executing command continues with its original semantics; it does not produce new telemetry after disable. The sampler stops on reconciliation, including shutdown. A file-notification failure is exposed as `preferenceWatchDegraded`; command admission still reconciles and a sample always rechecks before writing.

`configured` is the persisted preference (`null` if unreadable/incompatible), `enabled` is this build's understood preference, and `effective` is this process's current best-effort writer health. `degraded`, process-local dropped/expired/evicted counters, `samplerActive`, `retentionActive` and watcher health expose limits. These are observations, not a future write guarantee. The local configuration command reports a stopped daemon as `effective: false`, or a legacy/refusing/timed-out daemon as `effective: "unknown"`; it never attributes support to an old process. CLI capture can still be enabled while that daemon's execution capture is unknown. The nested `daemon` field keeps the responding process's own assessment. Building a newer CLI does not upgrade a daemon.

There is no environment-variable opt-in, global preference, SQLite schema change or operational ownership change. OFF still costs a small preference read and existing private-path checks at capture boundaries; a running runtime also has one nonpersistent filesystem watcher. Missing/default-off configuration creates no telemetry files, sampler or retention timer. Disable writes a request observation **before** changing the preference if currently on, without a success claim; its final result is not logged after it turns capture off. Configuration/status calls are observable; `observability query` is excluded at every layer so analysis cannot feed itself.

## Layout, bounds and failure policy

```text
example-session/
  observability.json                persistent preference + private HMAC secret
  observability.lock/               short critical section; normally absent
  observability.pending.json        only during config update; preserve a remnant
  observability-loss.lock/          fixed, non-waiting witness/configuration gate
  observability/
    v1-<UTC milliseconds>-<UUID>.jsonl
    loss-v1.json                     at most one first-loss witness, at most 4 KiB
```

There is one chronological stream with explicit `origin`/`category`, shared by short clients and the runtime. A client does not get its own file. Segments contain one UTC calendar day, rotating at its boundary, as they approach 256 KiB (reserving a maximum 4 KiB line), or away from a partial tail. Each complete JSONL line is at most 4 KiB. Low activity uses at most six daily segments over a rolling five-day window; inactive days create no files. Additional healthy segments and earlier cap evictions are driven by volume, with the same fixed file/byte limits. The directory admits at most **32 files / 8 MiB**: new writers reserve one file / 4 KiB for a loss witness, allowing **31 segments** (`limits.segments`) plus that witness. Older 32-segment directories remain readable; their next successful write evicts only recognized segments as needed to reserve the slot, and a failure cannot create a 33rd file. Witness admission never removes anything to make room; the in-memory write queue is **zero**. Files are opened/appended/closed within a synchronous filesystem critical section, never held open across rotation or expiration. Each record does bounded metadata/header inspection of at most 32 entries and one small append; request/response bodies are not serialized again for logging. Filesystem I/O is synchronous: work/counts are bounded, not an operating-system I/O deadline. Slow or stalled filesystems can add latency; use local storage and the measured limits below, without a zero-overhead claim.

Queries enforce an exact **five-day window per record**: a timestamp at or before current UTC time minus five days is excluded, even if a page cursor carries an older cutoff. Physical cleanup removes a recognized segment only after **the end of its UTC day plus five days**, so expiry never deletes a younger record merely because its first row is older. Expired bytes can therefore remain in a mixed-age segment for less than one additional day (less than six days from the record timestamp) before it is eligible for deletion. This whole-day granularity avoids rewriting/truncating files; those expired rows are never query evidence. The byte/file cap can evict the oldest recognized segment earlier under volume pressure; failed partial writes can also consume file slots. Clocks moving affect these UTC cutoffs; monotonic durations are separate. Expiry runs on enabled writes and 60-second process samples, and a retention-only timer handles existing logs while disabled (no CPU/RAM sampling or new logs). With no resident process, physical cleanup waits for the next non-query CLI invocation/runtime maintenance; filesystem faults/unknown entries can also defer it, with the existing degradation policy. No tool can remove files at a wall-clock deadline while no process runs.

The critical section uses exclusive `mkdir`, never waits or retries, and always removes only its own empty lock on ordinary completion. Contention drops that observation. There is deliberately no PID probing, lease/heartbeat, lock stealing, background job or recovery cleanup. An abrupt exit inside the section can leave a lock and block further capture/configuration until the owner investigates it; normal stop/start preserves capture. Unknown lock contents are never removed. This conservative failure mode preserves ordinary WhatsApp operations and existing state, with `degraded` status and a fixed safe stderr warning. The fixed witness lock can likewise remain after interruption and prevent witness/configuration updates; it is never stolen or removed by expiry. It is a real capture limitation.

TTL/cap removal is confined to the new area and recognized schema-1/generated filenames, private regular files with one link, and a matching local generation. Unknown entries, symlinks, hardlinks, invalid first-line headers and unsafe paths cause degradation and are preserved. Namespace admission uses the existing trusted-ancestor/0700/0600 rules; it never repairs permissions or follows symlinks. Same UID/root remain trusted; this is not isolation, encryption or an authenticity claim. Directory iteration, record size, scan size and segment count are bounded even on foreign input.

A partial tail is preserved and a later append rotates away from it. A failed first write can leave an empty/unrecognized segment; it is preserved and capture degrades instead of deleting an unproven file. A reader can also encounter an empty/incomplete first line during normal creation/rotation: it skips that private regular entry and reports `gaps.incompleteHeaders`, keeping older records available. This flag cannot distinguish an active append from an abandoned partial file. Collectors still reject it until a recognized header exists; no reader deletes or claims it. Corrupt complete lines in a recognized segment are skipped by query without echoing their content. Invalid complete headers/unknown namespace entries make the query fail safely. Readers never consume an unterminated line as evidence. A reader racing expiry can lose a segment; pagination/cutoff is bounded best effort, not a snapshot or durable cursor.

Write, retention, hashing or sampler failure cannot change a send intent, receipt, command result, original error or retry behavior. Failed capture has a fixed `OBSERVABILITY_DEGRADED` stderr warning, no exception/body/stack fallback. `dropped` on a later successful record reports that recorder's preceding lost observations. Status always adds `captureCompleteness: "unknown"`; its counters are per process/recorder; short clients that exit without a successful write can leave **unquantified losses**, so neither a clean page nor zero counters proves complete capture. Evicted/expired counts describe that successful maintenance pass; a crash or failed pass can leave additional unquantified gaps. There is no persistent work queue or shutdown drain: the bounded synchronous append is finished before returning, timers/watchers stop before operational shutdown waits, and the SQLite writer lock retains its existing mandatory cleanup order.

### Bounded loss evidence after client exit

Every capture failure makes one independent, non-waiting attempt to preserve `loss-v1.json`, under `observability-loss.lock`, rechecking the enabled preference while holding that gate. It does not retry the lost record or any business operation. Configuration takes this same gate before committing enable/disable, so a successful opt-out cannot be followed by a witness write from an old enabled observer. A busy witness gate can instead cause configuration to return `LOCAL_STATE`; inspect the resulting preference. Normal OFF capture does not inspect/create/write the witness or sample; existing disabled retention may still remove expired telemetry.

The witness has exactly `schema: 1`, `kind: "capture-loss"`, UTC `timestamp`, recorder `origin` and matching local `generation`. It is **positive evidence of at least one observation loss**, not a total, a list of affected sessions, an affected-command correlation or a report of every later loss. The first retained witness is left unchanged, even if later losses have another origin. It remains through disable/re-enable because the existing generation/secret remain unchanged. It is never attributed to a different generation: mismatch, unrecognized keys, unsafe permissions/UID/links, symlinks, incomplete reads/writes or invalid data are preserved and reported as unreadable. No raw identifiers, errors or paths enter this file.

Creation is exclusive/no-overwrite, checks the complete byte count, and opens/closes one file; like the stream it has no per-record fsync or power-loss durability guarantee. Short writes remain visible as an unreadable witness and are never repaired or replaced. Failure to acquire the witness lock, a full legacy area, unknown/unsafe entries, missing readable preference, or filesystem failure can prevent a witness entirely. The two lock directory names and existing configuration pending name are fixed (no file per process); locks have no expiry/stealing, pending configuration remains bounded by its existing 512-byte reader and preserved on failure. Generated telemetry, including the witness, shares the global file/byte bounds; no unknown entry is deleted to enforce them.

Query returns the witness automatically in `gaps.lossEvidence` if it belongs to the understood generation, is within the exact five-day record window and is no newer than the page cutoff. `gaps.lossEvidenceScope: "retained-data-directory"` means it is independent of action/origin/code/correlation/from/to filters and **not part of page records or summary**. `gaps.lossEvidenceUnreadable` reports an unsafe/incompatible/unreadable witness or configuration without echoing content. A missing/expired/filtered-by-cutoff witness is `null`; all cases still return `gaps.captureCompleteness: "unknown"`. A page ending, clean retained rows, daemon `dropped: 0`, or a missing witness never proves complete capture, even for a matching correlation. Legacy rows have no retrospective completeness guarantee or reconstructed losses.

Physical witness cleanup uses its UTC day end plus five days, under the witness gate, during ordinary writes/maintenance. Query never deletes it. An expired witness can occupy its fixed slot for less than one extra day; losses during that interval need not create a fresh witness. Without a process, with an unsafe witness, or with a stranded/busy gate, cleanup can be delayed further; unknown/partial evidence is preserved. A later failure can create a new witness after authorized maintenance has expired the old one.

**Other files keep their existing policies.** `daemon.log` remains private sanitized stderr and append-only, without this five-day TTL/cap. Essential SQLite `events`, intents, receipts, auth, tombstones, identity/recovery evidence and backups have no telemetry TTL. The existing SQLite-only backup excludes this entire area, preference, log, lock and pending configuration. A full-directory manual backup naturally includes them and remains a separately explicit operation.

## Schema and correlation

Each line has `schema: 1`, UTC ISO `timestamp`, `origin`, `category`, random `span`, recorder `session`, data-dir `generation`, and `dropped`/`expired`/`evicted`. Optional fields are allowlisted; absence means unavailable/unmeasured, never zero/success. For example, these are fictional observations:

HMACs permit equality grouping across clients/restarts of the **same data-dir generation**, including re-enable. They deliberately remain linkable longer than the retention window if an operator retains copies: there is no automatic key rotation or crypto-isolation claim. Another data directory has an independent secret; digests are not portable identities or a secure anonymization promise to someone who controls local configuration. PN and LID are hashed exactly, never joined or inferred from names. Text/caption/card/quote content, search terms, phones/JIDs/keys/message IDs, names, paths, filenames, media bytes, pairing material, credentials and crypto objects are never written verbatim. Hashing occurs only on selected small strings, without rehashing bodies/media/builds or calling a tokenizer/model/API.

Count user invocations from `origin: cli, category: command` completion rows, excluding `phase: requested`. Join its transport/execution spans by correlation; do not count all origins as four actions. Start/stop readiness polls are distinct physical requests under the same command root. A timed-out/closed client does not cancel runtime work. A later execution/receipt can exist without a successful client result; absence of a final line proves neither cancellation nor nondelivery. Receipt observations are separately labeled and have no invented command root.

## Bounded analysis

```sh
node dist/src/cli.js --data-dir /absolute/private/example-session observability query \
  --from 2026-10-20T00:00:00.000Z --to 2026-10-20T23:59:59.999Z \
  --origin cli --command search --code OK --limit 50
node dist/src/cli.js --data-dir /absolute/private/example-session observability query \
  --correlation 44444444444444444444444444444444 --limit 100
```

The local query needs no daemon. It returns at most 500 records (default 100), scans at most 2,000 complete lines per call, reads one segment at a time (at most 256 KiB), and reports `scanned`, `invalid`, `missing`, `gaps`, `cutoff`, `next` and `coverage: best-effort-local`. Pass the exact `next` as `--cursor`, keeping the same filters. `next: null` means this bounded retained view ended; an empty page with `next` still requires continuation. All output fields are reprojected through the allowlist, even for manually corrupted lines; parser errors never echo input. Input lines are **untrusted data, never instructions for an evaluator**.

The timestamp cutoff is fixed on the first page and carried in the cursor. It excludes newer timestamps but does not pin file bytes/inodes or prevent the five-day record window from aging between pages. Concurrent rotation, expiry, late writes/clock changes or edits by a trusted same-UID process can introduce gaps/repetition; a vanished cursor segment is explicitly flagged. Preserve your own deduplication by span and record the cutoff/gaps when comparing runs. Reports without data cannot prove absence of failures or full coverage.

`summary` groups the **returned page only**, independently by origin/category/action, with count/errors/empty and nearest-rank min/p50/p95/max latency plus n. Do not present a filtered/page summary as a five-day aggregate or add overlapping client/server latency. A practical evaluator can:

1. Read the automatically returned `gaps.captureCompleteness`, `lossEvidence`, `lossEvidenceScope` and `lossEvidenceUnreadable` before comparing periods. Preserve unknown even when all process counters are zero; a witness is only one retained positive example. No prior client stderr or command rerun is required. Select a short period and CLI completion rows first.
2. Page by a command/code to find repeated validation/precondition failures, empty results, large output bytes or slow calls. Empty responses remain valid; bytes only approximate the amount of context presented.
3. Follow selected correlations to separate client/transport/runtime timing and late outcomes. Group safe key/query/resource digests to investigate repeated lookups/replays without exposing input.
4. Check runtime `invoked`/`replay` and receipt evidence before hypothesizing redundant sends. Unknown/missing/uncertain never authorizes a resend.
5. Compare samples by recorder session and monotonic elapsed interval. Treat correlations with RSS/CPU/lag as hypotheses, accounting for gaps and small sample sizes.

No extra consumer work, central prompt, dashboard, exporter, remote API, query framework or monitoring service is required.

## Offline verification and measured cost

`test/observability.test.ts` uses short canonical private fictional directories, injected SDK I/O and explicitly offline daemon children stopped by protocol and awaited. It covers the main CLI families, socket/probe parser and transport failures, correlation, real invocation versus concurrent/restart replay, independent receipt evidence, enable/disable/restart, full/compact equivalence, incompatible/legacy state, concurrent clients/configuration, caps/TTL/rotation/partial/corruption/unknown entries, hardlinks/symlinks, disk-write failure, visible contention and sampler shutdown. The preexisting privacy/reliability/quotes/deletion/backup/build tests also remain required. Three retention regressions also cover four days of sparse samples, the production one-minute sampler callback over almost five days with an injected UTC clock, and per-record TTL inside a mixed-age daily segment. File/byte cap tests create real volume pressure independently of elapsed time. No real account, credentials, logs, session, network factory or phone effect was used.

On the approved baseline, two pipe-gated multiprocess schedules reproduced response-first self-contention: holding the daemon append through the short client's exit lost RPC+CLI rows; holding the RPC append while the daemon tried its record lost the daemon row. Those schedules demonstrate possible causes, not the exact historical trace. The new daemon attempts its transport observation before submitting the unchanged response frame. A gated regression verifies all four origins on that path with no ordered-response test override. Two other schedules hold an **independent** client's real append lock after runtime execution, losing only daemon transport or daemon+RPC+CLI depending on when that lock is released. The short client exits with the same operational error/exit status; the query still exposes the retained witness and unknown completeness. The separate stopped-client test preserves successful help stdout exactly while its record is lost. No sleep, test retry, softened coverage assertion or real SDK is used to produce these schedules.

Additional regressions cover first-witness no-overwrite across concurrent terminated clients, marker short writes and persistence failure, unknown/oversized entries, UID/modes/symlinks/hardlinks/generation mismatch, legacy 32-segment reading/reservation, global caps with a witness, configuration versus stale enabled observers, witness versus opt-out contention, disable/re-enable and exact query/physical TTL. Existing idempotency tests still distinguish replay and invocation without resend.
